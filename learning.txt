## 2026-07-29 — Location Selection: Karak Main Bazar vs. Sabir Abad

I compared two nearby coordinates for the project location before settling on one.

**Locations tested:**
- Karak Main Bazar: 33.1189° N, 71.0947° E
- Sabir Abad: 33.1384° N, 71.1909° E (closer to my home)

**Results (last 30 days, hourly, after timezone fix):**

| PM10 cross-source r | 0.523 | 0.522 |

**Decision:** Keep Sabir Abad as the active location.

**Why:** The two points are only about 9 km apart. Open-Meteo and OpenWeather return essentially the same grid-cell values for both. Cross-source correlations differ by less than 0.004, meaning data quality is identical. Sabir Abad is closer to my home, making the forecast personally relevant.

## 2026-07-29 — Timezone Fix: The Root Cause of Low Correlation

When I first compared Open-Meteo and OpenWeather data, the PM2.5 correlation was only about 0.4. This seemed suspiciously low for two sources drawing from similar atmospheric models.

**Root cause:** Open-Meteo returns timestamps in Asia/Karachi time, while OpenWeather returns UTC. Without normalizing both to the same timezone, the two datasets were shifted by 5 hours. This misaligned the diurnal AQI cycle — morning peaks in one source lined up with afternoon values in the other.

**Fix:** I normalized all timestamps to Asia/Karachi (UTC+5) at ingestion time.

**Results after fix:**
- Hourly PM2.5 correlation: 0.4 → 0.68
- Daily PM2.5 correlation: 0.4 → 0.77
- Testing a +120 minute shift only raised r to 0.697, confirming that timezone alignment — not hour-boundary offsets — was the dominant issue.

**Lesson:** Always normalize timestamps to a single timezone before comparing or merging data from different APIs. This single fix improved correlation more than any model tuning could.

## 2026-07-29 — WAQI/Peshawar Station: Stale Data

I checked the WAQI (World Air Quality Index) feed for the nearest station — Peshawar US Consulate, about 120 km from Karak.

**Finding:** The reported timestamp was 2025-03-04 — over four months old at the time of checking. The station data was completely stale.

**Implication:** WAQI cannot be used as a live validation source for Karak. The nearest ground monitor is too far away and its data is not current.

## 2026-07-29 — Multi-Pollutant Correlation Analysis

After the timezone fix, I computed cross-source correlations for all pollutants (last 30 days, hourly):

| Pollutant | Pearson r |
|---|---|
| O3 | 0.697 |
| PM2.5 | 0.680 |
| NO2 | 0.663 |
| PM10 | 0.574 |
| CO | 0.481 |
| SO2 | 0.437 |

**Interpretation:** The 0.4–0.7 range is the realistic agreement for modeled rural data from two different atmospheric models. It is not caused by a single bad pollutant or by timestamp offsets (verified: timestamps align exactly after normalization). The remaining disagreement reflects genuine model-to-model differences in how each API parameterizes emissions and atmospheric chemistry over Karak's complex terrain.

**What I learned:** Correlation between two models is not the same as accuracy against ground truth. These numbers tell me the models agree roughly, but neither can be validated without a local monitoring station.

## 2026-08-21 — Architecture Decision: Static JSON Serving + Data Repo Split

By late August, the CI pipelines were running hourly and committing forecast JSON files directly to the main karAQI repo. Within days, the commit history was overwhelmed with "ci: refresh forecast JSON" commits, making it impossible to see actual code changes.

**Solution — two repos:**
1. `karAQI` (code repo) — source code, models, notebooks, tests, CI workflows
2. `karAQI-data` (data repo) — CI-generated JSON files (static_forecast.json, model_eval.json)

**How it works:**
- CI workflows push JSON files to karAQI-data using a fine-grained GitHub PAT (`DATA_REPO_TOKEN`).
- The Streamlit dashboard reads these JSONs via raw GitHub URLs (`raw.githubusercontent.com`).
- `st.cache_data(ttl=300)` caches the JSON for 5 minutes, so every visitor gets near-instant page load.
- Zero runtime inference — the model never runs when someone opens the dashboard.

**CI schedule (final):**
| Pipeline | Schedule (UTC) | Purpose |
|---|---|---|
| Feature | Hourly :01 | Fetch data, build features, run tests |
| Forecast | Hourly :04 | Run inference, fetch Open-Meteo AQ ref, export JSON |
| Training | Daily 00:00 | Train all models, register in MLflow, export eval JSON |

## 2026-08-21 — IQAir Replaced by Open-Meteo

I initially used IQAir as the comparison reference on the dashboard — scraping their website for live AQI values. This failed because IQAir aggressively rate-limits anonymous scraping. GitHub Actions runners (cloud IPs) were blocked after just a few requests, returning 429 errors.

**Options considered:**
1. Add API key (paid, not free) — rejected for serverless constraint.
2. Use AccuWeather (has AQI API) — requires API key.
3. Use AQICN API (free token, 1000 req/min) — possible but adds another dependency.
4. Use Open-Meteo AQ forecast API — free, keyless, same EPA AQI scale.

**Decision:** Replaced IQAir with Open-Meteo's AQ forecast endpoint. It provides 96 hours of hourly US AQI for Karak, free and keyless. The 96-hour response is trimmed to 72 hours from the forecast origin to match our model's window.

**Files removed:** `src/fetch_iqair.py`, `.github/workflows/iqair_pipeline.yml`

**Lesson:** If a data source requires scraping HTML from a website, it will break when run from cloud infrastructure. Use official APIs whenever possible. If no official API exists, the comparison source is not reliable enough for automated pipelines.

## 2026-08-21 — CI Pipeline Push Failures

The CI workflows that push JSON to karAQI-data failed silently for hours before I noticed.

**Root cause:** The pipeline had `exit 0` on clone failure — it printed "skipping push" and reported success. GitHub Actions showed green checkmarks, but the JSON was never updated. The dashboard kept showing stale data from the previous successful run.

**Fix:** Changed `exit 0` to `exit 1` with clear error messages. Workflows now fail visibly when the token is missing or the clone fails.

**Lesson:** Pipeline failures must be loud. Silent success on partial failure is worse than a visible error — it gives false confidence that the system is working.

---

## 2026-08-21 — Training Pipeline Push Race Condition

The training pipeline failed with: `error: cannot pull with rebase: You have unstaged changes`.

**Root cause:** The pipeline generated `model_eval.json` (creating an unstaged change) before trying to pull-rebase the data repo. Git refused to rebase with dirty working tree.

**Fix:** Added `git stash` before the pull-rebase step, then `git stash pop` after.

---

## 2026-08-22 — Dashboard Stale Predictions

The dashboard was showing predictions from 4:00 PM when it was already 6:00 PM.

**Root cause:** Same as the silent push failure — the forecast pipeline generated the correct JSON but failed to push it. The dashboard served the last successfully pushed file.

**After fix:** The pipeline now fails loudly, and the dashboard footer shows a note explaining that GitHub Actions delays (5–30 minutes, sometimes longer) can cause the hero AQI to reflect a previous hour.

## General Lessons Learned

1. **Timezone normalization is critical.** A 5-hour offset dropped correlation from 0.68 to 0.4. Always normalize at ingestion.

2. **Cross-source correlation ≠ ground-truth accuracy.** Two models agreeing does not mean either is right. Be honest about what validation can and cannot prove.

3. **Persistence is a strong baseline.** "Tomorrow = today's AQI" is hard to beat at 72 hours. Any complex model must prove it is better.

4. **Silent pipeline failures are dangerous.** Always exit with a non-zero code on failure. Green checkmarks with stale data are worse than red crosses with error messages.

5. **Separate dashboard and CI dependencies.** Streamlit Cloud installs everything in requirements.txt. MLflow's pyarrow dependency needs cmake, which Streamlit Cloud does not have. A lean `app/requirements.txt` solves this.

6. **Data repos keep commit history clean.** Hourly JSON commits to the main repo bury real code changes. A separate data repo with raw GitHub URL access is the standard pattern.

7. **Static serving beats runtime inference for dashboards.** Pre-computing predictions via CI gives every visitor instant page load.

8. **Cron triggers are best-effort.** GitHub Actions scheduled workflows are frequently delayed. Design the system to tolerate this.
